Nightfix

Quieter nights

Opensource incident response that runs in your own AWS account. When an alert fires, Nightfix runs the fix you'd have run at 3 a.m., and only wakes someone up if it doesn't work.

3:07 a.m., and nobody wakes up

A CloudWatch alarm fires on checkout-api. This is the incident's own timeline, the way Nightfix records it.

  1. 03:07:12

    The alarm fires

    ecs-unhealthy-checkout crosses its threshold, and an incident opens on checkout-api.

  2. 03:07:12

    The known fix starts

    The ecs-service-restart runbook matches the alarm. The page is held for up to two minutes while it runs.

  3. 03:07:13

    The agent checks before it acts

    The agent in your VPC verifies the runbook's signature, then forces a new deployment of the service under its own IAM role.

  4. 03:08:41

    The service is healthy again

    The runbook's last step waits until ECS reports the service stable.

  5. 03:09:40

    The alarm clears

    CloudWatch reports OK, the incident resolves itself, and Slack gets a summary for the morning.

  6. Nobody was paged.

If the fix doesn't work, on-call is paged straight away through PagerDuty, with what was tried. When the alarm clears, the page resolves itself.

How it works

Three parts, all running in your account.

  1. Alerts come in

    From CloudWatch through SNS, or from any tool that can send a signed webhook. Repeats of the same problem fold into one incident.

  2. Runbooks do the known fix

    Runbooks are YAML you review like code. Every version is signed, and risky steps wait for a teammate to approve them in Slack.

  3. People get paged when it matters

    If the fix fails or the alert doesn't clear, Nightfix pages through PagerDuty with what it tried. Critical incidents page straight away.

Everything stays in your account

Nightfix is built to run code in production safely, so it assumes the worst about everything around it, itself included.

  • Nothing calls home. The control plane, its database and its keys run in your AWS account.

  • Outbound only. The agent connects out over mutual TLS. You open no inbound ports.

  • No tokens to leak. Agents enroll by proving their IAM role.

  • Signed runbooks only. You can also limit an agent to the exact runbooks you've approved.

  • Secrets stay put. They're read from Secrets Manager or SSM at run time and scrubbed from output.

  • Every action is recorded in a tamper-evident audit log.

Fits what you already run

Bring your own VPC, DNS, database, KMS keys and permissions boundary. Nightfix uses them instead of creating its own.

Alerts
CloudWatch, signed webhooks
Paging and chat
PagerDuty, Slack
Sign-in
Okta, Google Workspace, Entra ID, Keycloak, Auth0, or API keys
Runs on
ECS Fargate or EKS, from Terraform modules and a Helm chart

Try it in a minute

The demo runs the whole loop on your machine: a real agent, a throwaway database, and stand-ins for AWS, Slack and PagerDuty.

Needs Go and PostgreSQL. To run it in AWS, start with the deployment guide.

git clone https://github.com/peacedouts/nightfix
cd nightfix
make demo        # fixed, nobody paged
make demo-fail   # fix fails, on-call paged
