# Nightfix — What's built

The detail behind the root README: what each part of Nightfix does today, and what's deliberately not built yet. The design docs in [design/](design) describe the intended design; this file says where the code differs.

## Built

| Area | What's real in this build |
|---|---|
| Ingest | CloudWatch via SNS with signature verification (v1/v2) and topic pinning; generic webhook with HMAC + 5-minute replay window, and each signed delivery accepted once (a repeat inside the window is acknowledged and not stored, so a replayed "resolved" can't silence a firing alert). The same body signed in the same second is one delivery; senders that can emit identical payloads that fast should make each body unique (an event id field, say; webhook alerts are timed on receipt). Raw event persisted before processing; `202` returned. |
| Dedupe & routing | Fingerprints (integration + `AlarmArn`, `dedup_key`, label hash), so one integration's messages can't touch another's alerts; events apply in the order they were received (CloudWatch: the order of their state changes), even when a later one commits first, and a CloudWatch state older than one already applied (an ALARM delivered after its OK) is ignored; re-fire within the reopen window reopens; ordered CEL routing rules; catch-all service so nothing is unrouted. Concurrency-safe via partial unique indexes. |
| Incidents | Grouping by service + labels within a window; severity = highest alert; lifecycle `remediating → triggered → acknowledged → resolved`; reopen pages without retrying auto-remediation; append-only timeline. |
| Remediate before paging | Held page bounded by `min(run timeout + verification, max_hold)`; resolves only if the run succeeds **and** alerts clear; pages on failure, timeout, lost agent, expired hold, or still-firing alert. Guardrails: org freeze, no healthy agent, cooldown, `maxRunsPerHour`, more than one auto runbook holding the page (`beforePaging`), no matching agent able to run the runbook's step types, flap guard (3 auto-fixes of one alert in 24h, counting fixes that later reopened). Critical incidents page in parallel, and their auto-fixes count as verified too. A fix whose alert re-fires within the reopen window is un-verified. |
| Notifications | Outbox delivered by concurrent workers on short leases: requests are sent outside any database transaction, so a hanging endpoint delays only its own row. Per-incident ordering (a resolve never overtakes its page) is index-backed. One org has at most a quarter of the workers in flight, and pages and resolves are claimed first. A claimed notification is seen through and recorded even during shutdown, and a worker that stalls past its lease can't send. Pages and resolves retry with backoff capped at 5 min (±20% jitter) for up to 24h, and after 3 failed attempts say so (an Error log line, which alarms, and an entry on the incident's timeline); updates and approval messages 8 times; `Retry-After` is honoured. PagerDuty Events v2 with the incident as `dedup_key`, so acknowledging an incident acknowledges the upstream page and resolving it resolves the page. Slack incoming webhooks. Tenant URLs are limited to `hooks.slack.com` and PagerDuty's event hosts, re-checked at send time, with no redirects and a dialer that refuses private, loopback and metadata addresses (`NIGHTFIX_DEV_ALLOW_PRIVATE_TARGETS=1` lifts this for local stubs). Stored errors are generic and never contain URLs. Credentials sealed per org and per purpose (a sealed value copied into another column, row or org doesn't decrypt); never logged or returned. |
| Runbooks | Strict YAML parsing, the full publish linter (no templating in `run:`, pattern or enum on alert-derived string params (int and bool are type-checked), auto triggers must list services, secrets only in env/files, read-only wait checks…), CEL bounded by a size-aware cost limit and a 250 ms deadline, at most 100 steps / 500 expressions / 10 retries, YAML anchors and aliases refused, `allowedRoles` enforced when a run starts, RFC 8785 canonical digests, Ed25519 signatures, immutable versions. |
| Runs & dispatch | Step-by-step dispatch from a Postgres queue (`SKIP LOCKED`), 30s leases, signed per-step envelopes bound to one agent with a 2-minute expiry. Lost non-idempotent steps go to `needs_human` and page; idempotent ones retry. Run timeouts. |
| Identity | Sign-in through Auth0 Organizations (each maps to an org) or any OpenID Connect provider (Okta, Google Workspace, Entra ID, Keycloak; one issuer maps to one org). RS256 tokens only, verified against the provider's JWKS (refreshed hourly; issuer, audience and expiry checked), and only tokens issued to the configured client IDs. Who may join is limited by IdP groups, email domains or required claims; users are provisioned on first sign-in, namespaced by issuer; IdP groups sync to teams. Scoped role bindings (org → teams → roles → scopes) enforced on runs, runbook publishing (including takeover protection) and incident actions; members without a binding are free viewers; only owners can grant admin or owner. API keys for automation: admins create, list and revoke them (`POST /v1/api-keys`, `GET /v1/api-keys`, `POST /v1/api-keys/{id}/revoke`); keys are shown once and stored hashed (a retry with the same `Idempotency-Key` within 24h returns the same response, kept sealed); only owners can create or revoke admin and owner keys; the org's last owner credential can't be revoked (create a new owner key first, then revoke the old one). If an owner key leaks and nobody can rotate it, an operator runs `nightfix org new-owner-key --org org_… --revoke-others` (on AWS: `deploy/scripts/new-owner-key.sh`). |
| Approvals | `approval` steps pause a run (`awaiting_approval`) until `count` people holding one of `fromRoles` (or higher) **within scope of the runbook and its target env** approve; re-checked at decision time; people only, never API keys; `excludeRequester` enforced in the API and by a database trigger; one vote per person; one rejection cancels; expiry times the run out. A held auto-remediation pages as soon as it needs an approval. Approve/reject from the API or Slack buttons: Slack's v0 request signature and 5-minute timestamp window are verified, `response_url` is pinned to Slack's host, Slack apps are registered per workspace by owners, a Slack user's link works only through the app it was made with, and Slack users are linked only by a one-time code issued by Nightfix to the signed-in user and typed into Slack (`/nightfix link`), never by profile email; the code never travels Slack-to-Nightfix, so the device-code phishing pattern doesn't apply. Slack approvals need a sign-in to this org within 7 days so IdP-synced teams stay fresh. Runbooks with `excludeRequester` can't be started by API keys. Freeze cancels waiting runs and blocks decisions; locks are always taken org → run → gate. Requests go to the incident's service Slack targets; runs outside an incident (or services with no Slack target) use the runbook team's approval channel, else the org default (`PUT /v1/approval-channels`); with none of those, the catch-all service's Slack targets, so a request is never sent nowhere. |
| Agent enrollment | **IAM by default**: the agent signs an `sts:GetCallerIdentity` request (never sent by itself) that covers the org and a single-use challenge nonce; the control plane builds the STS URL itself (no SSRF), has STS verify the signature, and matches account + role to an enrollment rule. Nothing long-lived to leak, no persistent disk needed. Denials are audited once the caller has proved an AWS identity (no matching rule, a revoked identity, a rule at `max_agents`) or holds a valid token; refusals before that (an invalid proof or token) aren't, so unauthenticated callers can't fill an org's audit log. Token enrollment remains as a fallback: a token lives at most 7 days and enrolls at most `max_agents` agents over its life. Agents and enrollment rules can be revoked (`POST /v1/agents/{id}/revoke`, `POST /v1/enrollment-rules/{id}/revoke`, optionally with its agents); a revoked rule's agents can't renew their certificates. |
| Agent | Key generated locally (CSR only), 24h mTLS certs with renewal, re-verification of everything before running (envelope signature, target agent, expiry, replay, bundle digest, **every required signer — locally pinned list wins**, allowlist — pinned by digest, since version numbers aren't signed — params, target labels). The step types an agent may run are set locally too (`NIGHTFIX_AGENT_STEP_TYPES`, e.g. no `shell`), so the control plane can't widen them. `aws` (SigV4 JSON-protocol calls), `wait`, and `shell` steps (minimal env, process-group kill on timeout). Secrets from Secrets Manager / SSM resolved on the agent and redacted from output and outputs, including values returned by `GetSecretValue`, SSM `SecureString` reads and KMS `Decrypt`, in plain, hex, base64 (at any offset for values of 7 bytes or more, wrapped at any width or not), URL- and JSON-escaped forms, across chunk boundaries; for a JSON secret, its secret fields rather than connection details. Redaction covers how tools print a secret, not a script that deliberately disguises one (reversing it, say): runbooks are signed and reviewed for that. Outputs over 1 MiB fail the step. Local freeze flag. |
| Tenancy & audit | Forced row-level security on every tenant table, app role that owns nothing, composite `(org_id, id)` foreign keys, `SECURITY DEFINER` functions as the only cross-tenant path. Hash-chained, append-only audit log (the app role can't update or delete it), verified on request (`GET /v1/audit-events?verify=true`, one at a time per org). |

## Not built yet, and differences from the design docs

- **No web UI** yet: the REST API plus Slack. No native paging (SMS, voice, schedules): Nightfix pages through PagerDuty. No Terraform provider for runbooks, no Git sync.
- **Step types**: `note`, `approval`, `shell`, `aws`, `wait`. `manual`, `python`, `http`, `container` and SSM execution are valid schema but rejected at publish until implemented. AWS calls support JSON-protocol services (ECS, Secrets Manager, SSM, DynamoDB, Logs, KMS); RDS and other Query/XML services aren't supported yet.
- **Customer co-signing** is designed (agent-protocol.md §3.3) but not built: there's no endpoint to attach a second signature, so the control plane's key is the only signer. To approve exactly what runs, use the agent's local allowlist in `enforce` mode.
- **Approvals are enforced by the control plane.** The agent runs a step after an approval because the control plane dispatched it; it doesn't verify signed approval evidence itself. The agent's allowlist and pinned key still bound what can run.
- **Agent transport** is mutual-TLS HTTPS with long-polling, not a gRPC stream. Messages, signatures, leases and failure semantics follow `agent-protocol.md`.
- **Keys**: the credential-sealing key is a KMS-wrapped data key; the agent CA and the per-org runbook signing keys live in Postgres, sealed by it, rather than in AWS Private CA or KMS. Signing-key rotation chaining isn't built, so pin the key in the agent (`required_signers`).
- **RBAC on reads**: scopes restrict writes (runs, publishing, incident actions); list endpoints aren't filtered by scope, so any member can view every incident and runbook. SCIM and custom roles come later.
- **Sign-in isn't cached**: each request with a user token re-syncs the user and their IdP teams.
- **Critical-hold grants** (decision #29) aren't built, so critical incidents always page in parallel, the documented default.
- `when:` is evaluated on the control plane, so it can't reference `target` yet (the linter rejects it).
- **API keys** don't expire and have one role, org-wide, until revoked (a role binding can add scoped roles to a key).
- **Notifications**: a page for a resolved incident stops after 8 failed attempts or 10 minutes; no 4xx is treated as permanent, so a page with a bad routing key retries for up to 24h. The notification client ignores `HTTPS_PROXY` (the address check must see the real destination).

The rest of the accepted gaps (rate limits, archival, KMS key policy and others) are listed in [deploy/README.md](../deploy/README.md#known-gaps-accepted-for-now).

## What the tests cover

The end-to-end tests cover: IAM enrollment (and its rejection of an unmatched role, a replayed nonce, an org/nonce that isn't inside the signature, a different STS action, and a forged signature), token enrollment as a fallback, sign-in through Auth0 and generic OIDC providers (client binding, group and domain gating, issuer namespacing), scoped RBAC (including republish takeover, privilege escalation, unlinked orgs, wrong audience, and group removal), auto-remediation with no page, a failed fix that pages and then auto-resolves upstream, an injection attempt in alert labels (refused by the parameter pattern; no ECS call is made), and forged or wrong-topic SNS messages (rejected before anything is stored). The database tests cover RLS isolation, cross-org write rejection, fail-closed queries without an org, composite foreign keys, and the audit chain.
